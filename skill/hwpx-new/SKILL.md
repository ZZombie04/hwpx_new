# hwpx_new — AI 작업 지침 (어떤 AI 든 이 파일만 읽으면 됩니다)

사용자가 **한글 서식 파일(.hwpx)** 을 주고 "이 서식으로 ○○ 만들어줘 / 계획서를 결과보고서로 바꿔줘 / 작년 문서를 올해로 고쳐줘"
처럼 요청하면, 아래 절차를 **추가 지시 없이 처음부터 끝까지 스스로** 수행하고 **HWPX 와 PDF 두 파일**을 돌려줍니다.
사용자는 초보자일 수 있으니 답변은 쉬운 한국어로 짧게 합니다.

## 0. 도구 준비 (한 번만)

- 이 저장소의 CLI `hwpx-new` 를 쓴다. (없으면 `pip install -e .` 또는 `pip install git+https://github.com/ZZombie04/hwpx_new.git`)
- MCP 도구가 연결되어 있으면 같은 이름의 도구(`hwpx_analyze`, `hwpx_build`, `hwpx_preview` …)를 쓴다. 기능은 동일하다.
- `hwpx-new doctor` 로 PDF 변환 엔진을 확인한다. (한글 설치된 Windows 가 가장 정확. 없으면 내장 렌더러가 근사 PDF 를 만든다.)
- 사용자가 `.hwp`(옛 형식)를 줬다면 `hwpx-new convert 파일.hwp` (Windows+한글) 로 `.hwpx` 로 바꾼다. 불가능하면 "한글에서 다른 이름으로 저장 → HWPX" 를 안내한다.

## 1. 서식을 분석한다

```
hwpx-new analyze 서식.hwpx        # 문서 구조: 표지/부제/소제목/표/박스/글머리, 뼈대
hwpx-new scaffold 서식.hwpx       # 서식 뼈대를 그대로 따르는 Markdown 초안
```

분석 결과로 다음을 **스스로 판단**한다.
- 이 문서는 무엇인가? (운영 계획서, 결과보고서, 안내 공문, 가정통신문, 신청서, 회의록 …)
- 소제목 번호 체계(Ⅰ. / 1. / 가.)와 문체(개조식 `~함.` / 경어체 `~합니다.`)
- 표의 종류(항목-내용 표, 일정표, 명단표 …), 강조 박스의 용도

## 2. 사용자 요청에 맞게 뼈대를 재구성한다 (변환 방침)

**서식의 모양은 도구가 그대로 복제한다.** 너는 **내용과 구조만** 정한다.

| 요청 | 재구성 방법 |
|---|---|
| 계획서 → 결과보고서 | 개요(계획→실적), 교육과정/일정(계획→실제 운영), 기수별·회차별 실적(참석·이수 인원), **운영 결과**, (연수·행사면) **만족도 조사**(리커트 표 + 서술 의견), **성과(기대효과 대응 달성)**, **향후 계획·제언**. 계획서의 표·박스 구조는 유지 |
| 결과보고서 → 계획서 | 실적 표현을 계획 표현으로(`~하였음` → `~한다`), 결과·만족도 절 제거, 기대 효과 추가 |
| 작년 문서 → 올해 문서 | 구조·문체 유지, 날짜·요일·인원·금액·기관명만 갱신, 요일 검증 |
| 공문·안내문 → 다른 대상용 | 수신·발신·제목·본문 구조 유지, 대상에 맞게 어투 조정 |
| 기타 | 서식의 소제목 뼈대를 기준으로 사용자의 자료를 채운다 |

원칙
1. 사용자가 준 **사실(날짜·인원·명칭·금액)은 그대로** 쓴다. 표·본문 어디서든 숫자는 서로 일치해야 한다(합계 검산).
2. **사용자가 주지 않은 사실을 임의로 만들지 않는다.** 필요한 정보가 결과를 좌우하면 짧게 물어보고, 사용자가
   "그럴듯하게/최고로 채워줘"처럼 명시적으로 위임했을 때만 만들어 넣는다. **만들어 넣은 내용은 최종 답변에 목록으로 반드시 알린다**
   (예: "만족도 점수·서술 의견·진행 시간표는 제가 만든 예시 값입니다. 실제 자료로 바꾸세요").
3. 문체·번호 체계는 서식 원문과 통일한다. 날짜에 요일을 쓰면 실제 요일과 맞춘다(2026. 9. 16.은 수요일).
4. 사람 이름·연락처 같은 개인정보는 서식 원문이 쓴 방식(예: 가림 표기)을 따른다.
5. 결과물이 A4 몇 쪽이 적당한지 생각한다. 보고서는 보통 2~5쪽. 한 셀에 너무 긴 글은 피한다.

## 3. 내용을 쓴다

`hwpx-new format` 으로 문법을 확인한다. 핵심은 Markdown:

```markdown
# 문서 제목
@subtitle 작성 부서
## Ⅰ. 소제목
- 글머리 문단
  - 하위 단계
:::box 강조 박스 제목
박스 안 줄 1
:::
<!-- widths: 1.3, 3.5 -->
| 항목 | 내용 |
|:-:|:-:|
| 연수명 | ... |
@end
```

병합 셀이 필요한 표만 JSON(`{"blocks":[...]}`)을 쓴다. 파일로 저장한다(예: `content.md`).

## 3-1. 사용자가 사진을 준 경우 (사진을 표·보고서에 넣어 완성)

"이 사진들 넣어서 결과보고서 만들어줘" 같은 요청이면 사진도 **스스로 파악해 알맞은 곳에** 넣는다.

1. **파일 경로 확보**: 사용자가 사진 파일·폴더 경로를 주면 그대로 쓴다. 채팅에 첨부만 됐고 파일 경로를 알 수 없으면
   "사진을 한 폴더(예: `사진/`)에 넣고 폴더 경로를 알려 주세요"라고 한 번만 요청한다(문서에 넣으려면 실제 파일이 필요).
2. **사진 살펴보기**: `hwpx-new photos 사진폴더` (MCP: `hwpx_photos` → `hwpx_photo_sheet`).
   촬영 시각 순 목록과 **번호가 붙은 한눈에 보기 이미지**(`_photo_sheet.png`)가 나온다. 이미지를 열어 각 사진이 무엇인지 파악한다
   (활동 장면, 단체 사진, 설문지, 현수막·자료, 기수 구분 등). 촬영 시각으로 진행 순서를 짐작한다.
3. **배치 결정**

| 사진 종류 | 넣을 곳 |
|---|---|
| 활동·실습 장면 여러 장 | 결과 보고의 "활동 사진"(또는 운영 결과) 절에 `:::photos columns=3 title="1기 실습 장면"` (기수·회차별로 나눔) |
| 단체·기념 사진 1장 | `![캡션](경로)` 단독 사진(활동 사진 절 끝 또는 개요 뒤) |
| 설문지·자료·현수막 등 증빙 | 해당 절의 표 셀에 `![](경로)` (표에 "사진 / 설명" 열을 둠) |
| 서식에 사진 절이 없음 | 보고서 성격에 맞는 위치(보통 운영 결과 다음)에 "활동 사진" 절을 새로 만든다 |

4. **캡션**: 사진에 실제로 보이는 것 기준으로 짧게 쓴다(`준비운동 실습(1기)`). 확신이 없으면 추측하지 말고 중립 표현(`연수 현장`)을 쓴다.
5. **한 쪽 분량**: 사진 대지는 한 표에 6~9장(3열)이 적당하다. 더 많으면 표를 나눈다.
6. **개인정보**: 학생 얼굴·명찰·연락처가 보이는 사진이 있으면 게시 동의가 필요할 수 있음을 최종 답변에 한 줄로 알린다.
7. 사진은 자동으로 회전 보정(EXIF)·축소(긴 변 1600px)·형식 변환(HEIC/WEBP → JPG/PNG)되어 HWPX 안에 들어간다.
   경로는 내용 파일 기준 상대 경로 또는 절대 경로. 빌드 후 미리보기로 사진 방향·잘림을 확인한다.

## 3-2. 사진·도면·양식이 많은 기존 문서를 다른 기관용으로 바꾸는 경우 (복제 방식)

예: 도교육청 경기 요강(사진·도면·종목 박스·동의서 양식 포함)을 지역교육지원청 운영 계획으로 바꿀 때.
**원본을 처음부터 다시 쓰지 말고** 원본 블록을 복제해 글만 바꾼다.

1. `hwpx-new analyze` 로 블록 번호를 확인하고, 원문 전체를 읽어 **무엇을 그대로 둘지 / 바꿀지 / 새로 쓸지** 표로 정한다.
2. 그대로 둘 것(사진·규격표·경기 방법·양식)은 `clone`(구간 복제), 기관명·대회명만 바꿀 곳은 `replace`, 새 내용은 `like`(기존 문단 모양 빌리기)와
   `table` + `proto`(기존 표 모양 빌리기)로 쓴다. 문법: `hwpx-new format`.
3. 원본에 있던 **지역 구분 표현 전수 치환**: 기관명·대회명·날짜·장소·"지역별 상이" 등. `replace` 후 결과 본문에 잔재가 없는지 검사한다.
4. 사용자가 준 **운영 조건**(참가 자격, 신청 방법, 시간·장소, 시상·특전)은 원본의 해당 항목을 **대체**하고, 원본과 달라지는 점은 한 표로 요약해 준다.
5. 빠지면 안 되는 항목(근거, 목적, 대상, 일정, 방법, 안전, 시상, 협조, 예산, 붙임 양식)을 체크리스트로 만들어 **최종본에서 글자 검색으로 확인**한다.
6. 수치·인원·등수 규칙은 서로 모순이 없게 합산 검산한다(예: 표창 4+6=특전 10교).
7. 사용자가 주지 않은 일정·금액 등은 지어내지 말고 "예산 확정 후 기재" 같은 빈칸이나 **(안)** 표시를 쓴다.

## 4. 만든다 → 눈으로 확인한다 → 다듬는다

```
hwpx-new build 서식.hwpx content.md -o 결과폴더 --name "문서 이름"
```

`build` 는 한 번에 다음을 수행한다: HWPX 조립 → PDF 변환 → **조판 자동 점검**(빈 쪽, 소제목만 쪽 끝에 남음, 표가 쪽 사이에서 잘림,
마지막 쪽 토막) → **자동 보정**(쪽 나눔 삽입·간격 압축, 최대 6회 반복) → 쪽별 미리보기 PNG 생성.

그다음 **반드시** 결과를 확인한다.
- 출력의 `남은 조판 문제`, `경고`(날짜-요일 불일치, 표 칸 수 불일치 등)를 읽는다.
- 이미지를 볼 수 있으면 `결과폴더/문서이름_미리보기/page_N.png` 를 모두 열어 본다(또는 MCP `hwpx_preview`).
  글자가 잘렸는지, 표 열이 너무 좁은지, 쪽이 어색하게 비었는지, 소제목이 홀로 남았는지 본다.
- 문제가 있으면 **내용을 고쳐서**(문장 줄이기, `widths` 조정, `<!-- pagebreak -->` 위치 변경, 열 수 줄이기) 다시 `build` 한다.
  보통 1~3회면 끝난다. 3회 넘게 반복하지 않는다.
- PDF 가 `내장 렌더러` 로 만들어졌다면 실제 한글에서의 쪽 배치와 조금 다를 수 있음을 사용자에게 한 줄로 알린다.

## 5. 최종 답변 형식

1. 만든 파일 경로 2개(HWPX, PDF)
2. 문서 구성 한두 줄 요약(몇 쪽, 어떤 절로 구성)
3. **지어낸 내용 목록**(있다면) 또는 "사용자가 주신 자료만 사용했습니다"
4. 확인이 필요한 항목(예: 실제 만족도 데이터로 교체, 사진 붙임 추가)

## 금지

- 서식 파일 원본을 덮어쓰지 않는다(결과는 항상 새 폴더에).
- 사용자가 열어 둔 한글 창/문서를 닫거나 종료하지 않는다.
- 사실을 지어내고 알리지 않는 것.
